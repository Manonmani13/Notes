01 Blocking vs Reactive

❌ Blocking (Traditional)

  • Thread waits until task finishes
  • Cannot do anything else
  • One thread per request
  • Used in Spring MVC, JDBC

✅ Reactive (Non-blocking)

  • Thread does NOT wait
  • Continues other work
  • Few threads, many requests
  • Used in WebFlux, WebClient
🍵

Blocking — You order tea. You stand and stare at the counter until it's ready. You can't move. That's blocking.

🍕

Reactive — You order food, get a token, sit down, browse your phone. They call you when it's ready. That's non-blocking.


FeatureRestTemplate (Blocking)WebClient (Reactive)
Thread model1 thread per requestEvent loop – shared threads
WaitingThread waits idleThread moves on
ScalabilityLimitedHigh
StyleOld/SynchronousModern/Async

String data = restTemplate.getForObject(url, String.class);

// ✅ Reactive – returns immediately, subscribes later
Mono<String> data = webClient.get().uri(url).retrieve().bodyToMono(String.class);
02 What is Spring WebFlux?

🌊 Spring WebFlux

A non-blocking, reactive web framework introduced in Spring 5. Built on top of Project Reactor and handles HTTP requests using reactive streams.

⚡ Non-blocking

  • No thread waiting
  • Event-loop based
  • Netty server

📦 Project Reactor

  • Mono – 0 or 1 item
  • Flux – 0 to N items
  • Reactive Streams API

🎯 Goal

  • More requests
  • Fewer threads
  • Less memory

✅ Use WebFlux When

  • Chat / notification apps
  • Streaming APIs
  • High concurrency
  • Microservices

❌ Disadvantages

  • Hard to debug
  • Steep learning curve
  • Bad with blocking DBs
  • Overkill for simple apps

📡 Core Vocabulary


TermWhat it means

SubscriberReceives the data
SubscriptionConnection between publisher and subscriber
BackpressureSubscriber controls how much data it receives
03 Mono & Flux

🔵 Mono — 0 or 1 item

  • Single API response
  • Get user by ID
  • Save one record

🟣 Flux — 0 to N items

  • Get all users list
  • Streaming / live data
  • File chunks
// Mono – single value
Mono<String> mono = Mono.just("Hello");

// Flux – multiple values
Flux<String> flux = Flux.just("Java", "Spring", "WebFlux");

// Mono – empty
Mono<String> empty = Mono.empty();

// Mono – error
Mono<String> error = Mono.error(new RuntimeException("Failed!"));

🎬 Three Ways a Stream Can End


onNext → onComplete

Normal — emits data then completes successfully

onComplete (empty)

No data — just completes with nothing

onError

Something went wrong — stream stops immediately

04 Reactive Stream Lifecycle
🍔

Mono/Flux = You ordered food  |  subscribe() = You confirmed the order  |  onNext = Food arrives  |  onComplete = Order done  |  onError = Order failed

1. Create

Define Mono or Flux — nothing happens yet

2. Subscribe

Trigger the pipeline — data starts flowing only now

3. onNext(value)

Each item emitted to the subscriber

4. onComplete / onError

Stream ends normally or with an error

💡 A Mono/Flux does nothing until you call subscribe(). It's lazy!
Mono<String> mono = Mono.just("Hello")
    .map(String::toUpperCase);

// Nothing runs until this line ↓
mono.subscribe(value -> System.out.println(value));
05 Execution Model

🐢 Traditional Blocking

  • 1 request = 1 thread
  • Thread blocks on DB/API call
  • 100 requests = 100 threads
  • Memory heavy, limited scale

🚀 WebFlux Reactive

  • Few threads, many requests
  • Thread never blocks
  • 2–4 threads can handle 1000+ requests
  • Memory efficient, highly scalable

🔄 How a Request is Processed


Step 1 — Request Arrives

Handled by Netty event loop thread

Step 2 — Controller Returns Mono/Flux

Does NOT send data yet — just a description

Step 3 — Non-blocking Call

Thread sends request (DB/API), registers callback, moves on immediately

Step 4 — Thread is FREE

Same thread picks up the next incoming request

Step 5 — Response Arrives

Callback fires, thread processes and returns result

06 Event Loop Model
👨‍🍳

Blocking (Old way) — One chef per customer. Chef stands idle while the oven heats up.

Event Loop (WebFlux) — One waiter takes 50 orders, sends all to kitchen, keeps taking new orders, delivers each one when it's ready. Nobody waits idle.

⚙️ Event Loop Internals


  1. Request arrives → assigned to event loop thread
  2. Thread starts task
  3. If I/O needed → register callback → MOVE ON
  4. Thread handles next requests freely
  5. When I/O completes → callback executes the result
✅ Threads are NOT tied to requests. They are continuously reused. 2–4 event loop threads can handle 1000+ concurrent requests.

08 Key Operators
map()

Transform each element synchronously. Returns a normal value.

flatMap()

Transform each element asynchronously. Returns Mono/Flux.

filter()

Remove elements that don't match a condition.

flatMapMany()

Convert Mono → Flux. Expand one item to many.

switchIfEmpty()

If stream is empty, switch to a fallback publisher.

zip()

Combine multiple publishers — emits only when ALL emit.

merge()

Merge publishers in parallel (order not guaranteed).

concat()

Run publishers sequentially one after another.

collectList()

Collect all Flux items into Mono<List>.

delayElements()

Add a delay between each emitted element.

take(n) / skip(n)

Take first N items or skip first N items.

buffer() / window()

buffer() → groups into List. window() → groups into Flux.

then() / thenReturn()

then() ignores result, waits for completion. thenReturn() emits a new value.

cache()

Store result and reuse it for future subscribers (performance).

share()

Convert Cold Publisher → Hot Publisher.

reduce()

Aggregate all items into a single value.

timeout()

Fail fast if no item arrives within a time limit.

doOnNext()

Side-effect: log/debug each element without changing the stream.

09 Error Handling
💡 In reactive programming, errors are part of the stream. Instead of try-catch blocks, we use operators on the pipeline.
onErrorReturn

Return a default fallback value when error occurs. Simple and direct.

onErrorResume

Switch to a fallback publisher (another DB/API call). Intelligent recovery.

doOnError

Log or monitor errors without recovering from them.

retry(n)

Retry the stream N times if error is temporary (network flakiness).

// onErrorReturn – simple fallback value
Mono<String> result = callExternalApi()
    .onErrorReturn("Default Data");

// onErrorResume – fallback API call
Mono<String> result = callExternalApi()
    .onErrorResume(ex -> callBackupApi());

// doOnError – just log it
Mono<String> result = callExternalApi()
    .doOnError(ex -> log.error("Error: {}", ex.getMessage()));

// retry – try again 3 times
Mono<String> result = callExternalApi()
    .retry(3);
10 Schedulers & Thread Switching
⚠️ Never run blocking code (JDBC, File I/O) on the event loop thread — it will block all other requests!

⚡ Schedulers.parallel()

  • CPU-intensive tasks
  • Calculations
  • Data transformations

🧱 Schedulers.boundedElastic()

  • Blocking operations
  • JDBC / File I/O
  • Legacy APIs

🔁 Schedulers.single()

  • Single reusable thread
  • Sequential tasks
  • Time-sensitive work
OperatorEffect
subscribeOn()Controls where the entire pipeline starts (from beginning)
publishOn()Switches thread mid-pipeline from that point onward
Flux.fromIterable(items)
    .subscribeOn(Schedulers.boundedElastic())   // start on blocking thread
    .map(item -> process(item))
    .publishOn(Schedulers.parallel())            // switch to CPU thread
    .map(item -> transform(item))
    .subscribe();
11 Hot vs Cold Publishers

🧊 Cold Publisher

  • Starts only when subscribed
  • Each subscriber gets fresh data
  • DB calls, API calls, file reads

🔥 Hot Publisher

  • Emits even without subscribers
  • Late subscribers miss past data
  • Live feeds, event streams
📺

Cold — YouTube video. Every viewer starts from the beginning. Each gets their own fresh stream.

🏏

Hot — Live cricket match. You join late, you miss the early overs. Data is live and shared.


// Cold → default Flux/Mono
Flux<String> cold = Flux.just("a", "b", "c");

// Hot → convert using share()
Flux<String> hot = cold.share();

// Cache → store result for future subscribers
Flux<String> cached = cold.cache();
12 Backpressure
🚰

Imagine a fire hose filling a small cup. Without backpressure — the cup overflows.
Backpressure = the cup telling the hose "slow down, I can only take 10 drops at a time."

📌 What is Backpressure?

The mechanism that lets a subscriber control how much data the publisher sends. Without it, a fast producer can overwhelm a slow consumer and cause memory issues.

onBackpressureBuffer()

Buffer excess items in memory until consumer is ready.

onBackpressureDrop()

Drop items the consumer can't handle in time.

onBackpressureLatest()

Keep only the latest item, discard older ones.

Flux.range(1, 1000)
    .onBackpressureBuffer(50)   // buffer max 50 items
    .subscribe(item -> {
        // slow consumer
        Thread.sleep(100);
        System.out.println(item);
    });
13 What is Streaming?
📦

Normal response — Waiter brings the entire meal at once when everything is ready. You wait longer.

🍽️

Streaming response — Each dish is brought as soon as it's ready. Starters first, then mains, then dessert.


📡 Use Cases for Streaming

Live Stock Dashboard WhatsApp messages Log streaming Large file download Real-time notifications Kafka consumers

@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)

15 WebClient Deep Dive
🌐

WebClient is the reactive replacement for RestTemplate. It is non-blocking, supports streaming, and can chain multiple calls together without blocking any thread.

⚙️ Setup WebClient

// Basic setup
WebClient client = WebClient.create("https://api.example.com");

// With custom config (timeout, headers)
WebClient client = WebClient.builder()
    .baseUrl("https://api.example.com")
    .defaultHeader("Authorization", "Bearer token")
    .build();
GET Request 
Mono<User> user = client.get()
    .uri("/users/{id}", 1)
    .retrieve()
    .bodyToMono(User.class);
POST Request 
Mono<User> saved = client.post()
    .uri("/users")
    .bodyValue(newUser)
    .retrieve()
    .bodyToMono(User.class);

🔗 Chaining Multiple Calls

// Get user, then get their orders — both non-blocking
Mono<Orders> result = client.get()
    .uri("/users/1")
    .retrieve()
    .bodyToMono(User.class)
    .flatMap(user -> client.get()
        .uri("/orders?userId=" + user.getId())
        .retrieve()
        .bodyToMono(Orders.class));

⚠️ Error Handling in WebClient

Mono<User> user = client.get()
    .uri("/users/99")
    .retrieve()
    .onStatus(HttpStatus::is4xxClientError,
        response -> Mono.error(new RuntimeException("User not found")))
    .onStatus(HttpStatus::is5xxServerError,
        response -> Mono.error(new RuntimeException("Server error")))
    .bodyToMono(User.class);
MethodPurpose
retrieve()Simple — just get the response body
exchangeToMono()Advanced — access full response (status, headers)
bodyToMono()Convert response → single object
bodyToFlux()Convert response → stream of objects
onStatus()Handle specific HTTP status codes
16 Functional Routing
💡 WebFlux has two programming styles. You know the annotation style (@RestController). Functional routing is the second style — more explicit and flexible.

📝 Annotation Style (you know this)

  • @RestController
  • @GetMapping, @PostMapping
  • Familiar from Spring MVC
  • Less flexible

⚙️ Functional Style (new)

  • RouterFunction
  • HandlerFunction
  • More explicit routing
  • Better for complex routing logic

🔧 Step 1 — Create a Handler

@Component
public class UserHandler {

    public Mono<ServerResponse> getUser(ServerRequest request) {
        String id = request.pathVariable("id");
        Mono<User> user = userService.findById(id);
        return ServerResponse.ok()
            .contentType(MediaType.APPLICATION_JSON)
            .body(user, User.class);
    }

    public Mono<ServerResponse> getAllUsers(ServerRequest request) {
        Flux<User> users = userService.findAll();
        return ServerResponse.ok().body(users, User.class);
    }
}

🛣️ Step 2 — Create a Router

@Configuration
public class UserRouter {

    @Bean
    public RouterFunction<ServerResponse> routes(UserHandler handler) {
        return RouterFunctions
            .route(GET("/users/{id}"), handler::getUser)
            .andRoute(GET("/users"),     handler::getAllUsers);
    }
}
ConceptRole
RouterFunctionDefines URL routes — like @GetMapping but in code
HandlerFunctionHandles the request — like a controller method
ServerRequestWrapper around HTTP request (path vars, body, headers)
ServerResponseBuilds the HTTP response (status, body, headers)
17 R2DBC — Reactive Database
🗄️

JDBC — Blocking. Thread waits while DB executes the query. Kills WebFlux performance.

R2DBC — Non-blocking. Thread moves on, callback fires when DB result is ready. True reactive database access.

❌ JDBC (Blocking)

  • Thread waits for DB result
  • Blocks event loop
  • JPA / Hibernate
  • Not reactive

✅ R2DBC (Reactive)

  • Non-blocking DB driver
  • Returns Mono / Flux
  • Works with PostgreSQL, MySQL, H2

18 Testing with StepVerifier
🧪

Normal assertEquals() doesn't work for async streams.
StepVerifier is the tool that lets you subscribe to a Mono/Flux and assert what it emits, step by step.

✅ Basic StepVerifier

// Test a Mono
Mono<String> mono = Mono.just("Hello");

StepVerifier.create(mono)
    .expectNext("Hello")   // assert value emitted
    .expectComplete()        // assert stream completed
    .verify();               // run it!

🔢 Testing Flux

Flux<Integer> flux = Flux.just(1, 2, 3);

StepVerifier.create(flux)
    .expectNext(1)
    .expectNext(2)
    .expectNext(3)
    .expectComplete()
    .verify();

💥 Testing Errors

Mono<String> error = Mono.error(new RuntimeException("Oops!"));

StepVerifier.create(error)
    .expectErrorMessage("Oops!")   // assert error message
    .verify();

⏱️ Testing with Time (Virtual Time)

// Without virtual time → test would take 10 real seconds!
Flux<Long> flux = Flux.interval(Duration.ofSeconds(1)).take(3);

// With virtual time → runs instantly
StepVerifier.withVirtualTime(() -> flux)
    .thenAwait(Duration.ofSeconds(3))
    .expectNextCount(3)
    .expectComplete()
    .verify();
MethodWhat it checks
expectNext(val)Next emitted value equals val
expectNextCount(n)Exactly n items emitted
expectComplete()Stream completed normally
expectError()Stream ended with error
expectErrorMessage()Error has specific message
thenAwait(duration)Advance virtual time
verify()Trigger the test — always call this!
19 WebSocket with WebFlux
📡

HTTP — Client asks, server answers, connection closes. One-way per request.

WebSocket — Client and server open a persistent two-way connection. Both can send messages any time. Perfect for chat, live scores, notifications.

🌐 HTTP (Request-Response)

  • Client requests → Server responds
  • Connection closes after each request
  • Polling needed for live data
  • High overhead for real-time

📡 WebSocket (Persistent)

  • One connection stays open
  • Both sides push messages freely
  • Low latency, low overhead
  • Great for chat, live feeds

🔧 WebSocket Handler (Server Side)

@Component
public class ChatWebSocketHandler implements WebSocketHandler {

    @Override
    public Mono<Void> handle(WebSocketSession session) {

        // Read messages from client, echo them back
        Flux<WebSocketMessage> response = session.receive()
            .map(msg -> msg.getPayloadAsText())
            .map(text -> "Echo: " + text)
            .map(session::textMessage);

        return session.send(response);
    }
}

🛣️ Register WebSocket Route

@Configuration
public class WebSocketConfig {

    @Bean
    public HandlerMapping webSocketMapping(ChatWebSocketHandler handler) {
        Map<String, WebSocketHandler> map = new HashMap<>();
        map.put("/chat", handler);   // ws://localhost:8080/chat

        SimpleUrlHandlerMapping mapping = new SimpleUrlHandlerMapping();
        mapping.setUrlMap(map);
        mapping.setOrder(-1);
        return mapping;
    }
}
✅ WebSocket + WebFlux is the ideal combo for real-time chat, live notifications, and live dashboards. The entire pipeline stays non-blocking.
20 Spring Security with WebFlux
💡 Spring Security works differently in WebFlux. It uses reactive types — no ThreadLocal, uses ReactiveSecurityContextHolder instead.

🔒 Spring MVC Security

  • SecurityContextHolder (ThreadLocal)
  • @EnableWebSecurity
  • Blocking filters
  • WebSecurityConfigurerAdapter

🔐 WebFlux Security

  • ReactiveSecurityContextHolder
  • @EnableWebFluxSecurity
  • Non-blocking filters
  • SecurityWebFilterChain

⚙️ Basic Security Config

@Configuration
@EnableWebFluxSecurity
public class SecurityConfig {

    @Bean
    public SecurityWebFilterChain securityChain(ServerHttpSecurity http) {
        return http
            .authorizeExchange(exchanges -> exchanges
                .pathMatchers("/public/**").permitAll()
                .anyExchange().authenticated())
            .httpBasic(Customizer.withDefaults())
            .build();
    }

    @Bean
    public ReactiveUserDetailsService userDetailsService() {
        UserDetails user = User.withDefaultPasswordEncoder()
            .username("admin").password("pass").roles("ADMIN").build();
        return new MapReactiveUserDetailsService(user);
    }
}

👤 Get Current User in Controller

@GetMapping("/me")
public Mono<String> currentUser(Authentication auth) {
    return Mono.just("Hello, " + auth.getName());
}

// Or using ReactiveSecurityContextHolder
public Mono<String> getUser() {
    return ReactiveSecurityContextHolder.getContext()
        .map(ctx -> ctx.getAuthentication().getName());
}

21 Context Propagation
🎒

In regular Java, you use ThreadLocal to carry data (like user ID, trace ID) through a request on the same thread.

In WebFlux, threads switch constantly — so ThreadLocal doesn't work. Instead, Reactor provides Context — a key-value bag attached to the reactive pipeline.

📥 Write to Context

Mono<String> result = Mono.just("Hello")
    .contextWrite(Context.of("userId", "user-123",
                              "traceId", "abc-xyz"));

📤 Read from Context

Mono<String> result = Mono.deferContextual(ctx -> {
    String userId = ctx.get("userId");
    return Mono.just("Processing for: " + userId);
}).contextWrite(Context.of("userId", "user-123"));
⚠️ Context flows upstream (from subscribe to source), not downstream. Always call contextWrite() after the operator that reads it.
ConceptThreadLocal vs Context
StorageThreadLocal → per thread | Context → per subscription
Thread-safeThreadLocal breaks on thread switch | Context is immutable & safe
Use caseCarry userId, traceId, auth token through the reactive pipeline

⚙️ Service

@Service
public class UserService {

    private final UserRepository repo;

    public Flux<User> getAllUsers()          { return repo.findAll(); }
    public Mono<User> getUserById(Long id)  { return repo.findById(id); }
    public Mono<User> createUser(User user)  { return repo.save(user); }
    public Mono<Void> deleteUser(Long id)   { return repo.deleteById(id); }

    public Mono<User> updateUser(Long id, User updated) {
        return repo.findById(id)
            .flatMap(existing -> {
                existing.setName(updated.getName());
                existing.setEmail(updated.getEmail());
                return repo.save(existing);
            });
    }
}

🌐 Controller

@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService service;

    @GetMapping
    public Flux<User> getAll() {
        return service.getAllUsers();
    }

    @GetMapping("/{id}")
    public Mono<ResponseEntity<User>> getById(@PathVariable Long id) {
        return service.getUserById(id)
            .map(ResponseEntity::ok)
            .defaultIfEmpty(ResponseEntity.notFound().build());
    }

    @PostMapping
    public Mono<User> create(@RequestBody User user) {
        return service.createUser(user);
    }

    @PutMapping("/{id}")
    public Mono<User> update(@PathVariable Long id, @RequestBody User user) {
        return service.updateUser(id, user);
    }

    @DeleteMapping("/{id}")
    public Mono<Void> delete(@PathVariable Long id) {
        return service.deleteUser(id);
    }
}
