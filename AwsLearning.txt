What is AWS EFS?
****************
Amazon Elastic File System (EFS) is a scalable, cloud-native Network File System (NFS) that allows multiple EC2 instances
 to access the same file system concurrently. It’s designed for Linux-based workloads and supports NFSv4.1 and NFSv4.2 protocols.

🔹 Key Features

Fully Managed: No need to provision or manage storage.
Elastic: Automatically scales up or down as files are added or removed.
Shared Access: Multiple EC2 instances can mount the same file system.
Durability & Availability: Data is stored redundantly across multiple Availability Zones.
Performance Modes:

General Purpose: Balanced for latency and throughput.
Max I/O: Optimized for higher throughput workloads.

🔹 Use Cases

Web serving and content management
Big data and analytics
Media processing workflows
Container storage (e.g., with Amazon ECS or EKS)
Home directories for users


🔹 Pricing
You pay for:

Storage used (GB/month)
Provisioned throughput (if using Provisioned Throughput mode)
Data transfer (cross-region or to/from on-premises)


🔹 How to Use EFS

Create a File System in the AWS Console.
Configure Mount Targets in each Availability Zone.
Mount the File System on EC2 instances using the NFS client.
Access Files just like a local file system.

What is RDS Auto Scaling?
Amazon RDS offers auto scaling for storage and read replicas (Aurora only). This helps handle unpredictable workloads without manual intervention.

Storage Auto Scaling: Automatically increases allocated storage when free space drops below a threshold.
Aurora Read Replica Auto Scaling: Adds/removes read replicas based on traffic load.
Aurora Serverless v2: Scales compute capacity up/down in seconds for both read and write workloads.


🔍 Key Features
----------------
Storage Auto Scaling

Triggered when:

Free space ≤ 10% of allocated storage.
Condition persists for ≥ 5 minutes.
At least 6 hours since last modification.

Adds storage in increments of:

10 GiB or 10% of current size, whichever is greater.

Requires setting a maximum storage threshold (e.g., 1260 GiB for a 1000 GiB DB).
Works with gp2, io1, io2 storage types.

Route 53 Routing Policies
****************************
1. Simple Routing Policy

Purpose: Routes traffic to a single resource (like one EC2 instance or one load balancer).
Use Case: When you have only one server or endpoint for your domain/subdomain.
Example:

Domain: example.com
Subdomain: app.example.com
You create a Simple record pointing app.example.com to an IP or ELB DNS name.


Behavior: No health checks or load balancing—just a direct mapping.


✅ 2. Weighted Routing Policy

Purpose: Distribute traffic across multiple resources based on assigned weights.
Use Case: Canary deployments or A/B testing.
Example:

Subdomain: api.example.com
Two endpoints:

api-v1.example.com → Weight 70
api-v2.example.com → Weight 30


Route 53 sends 70% traffic to v1 and 30% to v2.


Behavior: You can adjust weights anytime for gradual migration.


✅ 3. Latency Routing Policy

Purpose: Direct users to the resource with the lowest latency based on their geographic location.
Use Case: Global applications with servers in multiple regions.
Example:

Subdomain: game.example.com
Two resources:

us-east-1 → ELB DNS
ap-south-1 → ELB DNS

A user in India will be routed to ap-south-1 for better latency.

Behavior: Uses AWS latency measurements to decide routing.

Failover Routing Policy
**************************
Purpose: Provides high availability by routing traffic to a primary resource and switching to a secondary resource if the primary becomes unhealthy.
How It Works:

You create two records for the same domain/subdomain:

Primary: Points to main server (e.g., app.example.com → Primary ELB).
Secondary: Points to backup server (e.g., app.example.com → DR ELB).

Attach health checks to the primary record.
If health check fails, Route 53 automatically routes traffic to the secondary.

Use Case: Disaster Recovery (DR) setup for critical applications.
************************
Geolocation Routing Policy
***************************
Purpose: Routes traffic based on the geographic location of the user.
How It Works:

You define records for different regions:

Example:

Users from US → us.example.com
Users from India → in.example.com
Default → global.example.com

Route 53 uses the user’s IP to determine location and routes accordingly.

Use Case:

Deliver localized content.
Comply with regional regulations.
Optimize performance for regional servers.

Amazon VPC lets you create a private, isolated network within AWS where you can launch resources like EC2, RDS, and more. It gives you full control over:
IP address ranges
Subnets
Route tables
Network gateways
Security settings

Key Components

CIDR Block
Defines the IP range for your VPC (e.g., 10.0.0.0/16).

Subnets
Divide VPC into smaller networks.
Public Subnet: Has internet access via Internet Gateway.
Private Subnet: No direct internet access; uses NAT Gateway for outbound traffic.

Route Tables

Control traffic routing between subnets and external networks.

Internet Gateway (IGW)

Enables communication between VPC and the internet.

NAT Gateway / NAT Instance

Allows private instances to access the internet without exposing them.

Security Groups & NACLs

Security Groups: Instance-level firewall.
NACLs: Subnet-level firewall.

Basic Architecture

VPC → Public Subnet (EC2 + IGW)
VPC → Private Subnet (EC2 + NAT Gateway)
Route tables define connectivity.


Why VPC?

Isolation and security.
Custom networking.
Hybrid cloud setups (VPN or Direct Connect).


VPC Peering
****************
VPC peering is a networking connection between two virtual private clouds
that allows them to communicate privately using private ip addresses.

why do we need vpc peering?
*************************
To connect resources in different VPCs without using public internet.
For secure communication between environments (e.g., dev and prod).
To share services like databases or internal APIs across VPCs.

Key Characteristics
*************************
Private Communication: Traffic stays within AWS backbone, not the public internet.
One-to-One Relationship: Each peering connection links two VPCs only.
No Transitive Peering: If VPC-A is peered with VPC-B, and VPC-B with VPC-C, A cannot talk to C unless you create a separate peering connection.
Same or Different Accounts: VPCs can belong to the same AWS account or different accounts.
Same or Different Regions: Supports inter-region peering.

How VPC Peering Works
**********************
Create a Peering Connection:

Initiator sends a request to the other VPC.
The other VPC accepts the request.

Update Route Tables:
Add routes in both VPCs pointing to the peering connection for the destination CIDR.

Update Security Groups:
Allow traffic from the other VPC’s CIDR range.

DNS Resolution:
Enable DNS resolution for private hostnames if needed.

Limitations
No Overlapping CIDR Blocks: VPCs must have unique IP ranges.
No Transitive Routing: Cannot route through a third VPC.
No Edge-to-Edge Routing: Cannot route traffic to VPN or Direct Connect through peering.
Bandwidth: Uses underlying AWS infrastructure, but not unlimited.


Use Cases

Multi-Account Architecture: Connect VPCs from different accounts.
Shared Services: Centralized logging, authentication, or database VPC.
Hybrid Cloud: Combine workloads across regions.


Alternatives

AWS Transit Gateway: For complex multi-VPC architectures.
PrivateLink: For exposing services privately without full VPC connectivity.
